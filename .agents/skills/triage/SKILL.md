# Triage

Use the repository's issue-tracker configuration to inspect the requested queue or ticket. Read-only triage returns recommendations; publishing comments, changing labels, or closing items must be within the user's requested action. Preserve prior decisions and resolved answers.

## Inspect and decide

- Read the ticket, relevant discussion and labels; inspect a named PR's diff too. Discover external PRs only if the tracker configuration enables that surface.
- Check the affected behavior and relevant contracts. For a bug, reproduce it when practical; for an enhancement, search for an existing implementation. Report confirmed, disproven, or insufficient evidence.
- Search existing rejection records by related concept when relevant; read [OUT-OF-SCOPE.md](OUT-OF-SCOPE.md) only when handling such a decision. Prior rejection is context, not automatic authorization to close a new issue.
- Use the configured label mapping. If absent, inspect existing labels and propose a mapping; missing setup does not block investigation. Ask only if an ambiguous mapping or conflicting state prevents the requested label change.

## Roles

Each classified item uses one category (`bug` or `enhancement`) and one state:

| State | Meaning |
| --- | --- |
| `needs-triage` | Awaiting evaluation |
| `needs-info` | Missing information needed to decide or implement |
| `ready-for-agent` | Scope and observable acceptance criteria are clear |
| `ready-for-human` | Requires human judgment or access; explain which |
| `wontfix` | Maintainer has decided to reject or close as already implemented |

When the user explicitly requests a state change, apply it without another confirmation or an unsolicited design interview. Do not create missing labels, post extra briefs, or close a ticket unless that action is included in the request. A state recommendation alone is not a closure decision.

## Briefs and follow-up

Read [AGENT-BRIEF.md](AGENT-BRIEF.md) when preparing an implementation brief. If scope is unclear, ask the smallest unresolved question and continue independent verification. A design interview can use [grill-with-docs](../grill-with-docs/SKILL.md); it does not require uninstalled skills or a generic Skill tool.

A `needs-info` note separates established facts from specific missing answers. Reuse these notes when resuming; do not re-ask answered questions. For a queue summary, show counts and concise items in age order so the user can choose a target.

Every triage comment or issue actually published starts with:

> *This was generated by AI during triage.*

Finish with the recommendation or confirmed changes, supporting evidence, and any unresolved input. Repository file edits follow the development workflow; triage alone does not authorize implementation or merging.
