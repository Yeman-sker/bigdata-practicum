# Rejected feature decisions

Use `.out-of-scope/<concept>.md` to retain a maintainer's explicit rejection of an enhancement. Reuse a matching concept record rather than creating one per issue. This directory is created only when there is a decision to record.

A record contains the decision, durable reason and links to the requests it covers. Technical constraints and product boundaries are useful reasons; temporary workload is a deferral, not a permanent rejection.

During triage, search related concepts and surface any relevant prior decision. The maintainer may confirm it, reconsider it or explain why the new request differs. Do not close a new issue merely because it resembles a past rejection.

Do not add bug reports or already-implemented features to this directory. For an already-implemented request, point to the working behavior and evidence instead.

When rejection and closure are authorized, record the decision, publish the reason and close the requested item. Repository file edits use the normal development workflow. If the decision changes, update the record; keep old requests as historical evidence and do not reopen them unless requested.
