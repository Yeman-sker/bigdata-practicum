## 1. 本轮要得到什么

让一位组员拿到自己的 Issue 后，不依赖聊天记录或另一位组员的实现分支，就能回答：

1. 我交付哪一部分，哪些相邻工作由别人负责？
2. 输入从哪里来，字段、时间、站点编号和空值是什么意思？
3. 输出交给谁，使用什么表、事件或 HTTP 接口？
4. 上游尚未完成时，使用哪份样例，预期结果是什么？
5. 怎样证明我完成了任务，何时可以接入真实链路？

本轮交付的是下列文档的职责、内容清单、编写顺序、待解决问题和完成标准。各份完整契约、最终人员安排、测试样例和真实联调证据，需要按本文继续落实，不能因本文存在就认定 #31 已通过。

### 配套资料怎么放

- README 保留项目简介、技术版本矩阵和阅读导航。新成员入口是“产品 → 架构 → 自己的接口 → 自己的 Issue → 运行手册”。
- docs/contracts/README.md 负责契约目录、公共命名/时间/身份语义和生产者—消费者索引；现有 Source Validator 用法保留。具体字段不复制到每份 Issue。
- ADR 记录决策理由、取舍、状态和后继文件。需求清单、全量字段表、每日排期分别由上表对应文档承载。
- GitHub Issue 是任务范围、验收标准和进度的事实来源；引用契约版本和位置。契约承载接口定义，两者必须一致，发生冲突时先更新关联记录。
- fixtures/ 继续作为共享测试样例入口；DDL、HTTP schema、预期结果属于契约交付物。样例不是第三套独立定义。
- docs/source/、docs/gbfs/、docs/hdfs-hive/、docs/spark/ 的 Day 1 实测记录保留，运行手册引用已有命令，避免再写一遍环境教程。

## 4. 每个跨模块交接都要有记录

每项交接使用同一记录格式：

| 要素 | 必填内容 |
| --- | --- |
| 身份 | 契约名称、版本/冻结提交、状态、对应 Issue |
| 职责 | 唯一主维护人、生产者、所有实际消费者；评审由相关生产者和消费者完成 |
| 数据 | 一行/一条消息的含义；字段、类型、nullable、枚举、单位、时区；键与唯一性 |
| 交付 | 表/路径/topic/HTTP 入口、更新方式、批次和可消费条件 |
| 行为 | 空、缺失、非法、重复、乱序、超时、过期；不适用的项注明原因 |
| 验证 | 共享正常及边界样例、明确预期结果、最小运行命令、关联验收场景 |
| 变更 | 影响哪些消费者、兼容性结论、需要同步的文件/测试/Issue |

需要覆盖的交接如下；负责人为基于现有分工的规划建议，具体工作边界在 delivery.md 中确认。

| 交接 | 生产者 → 消费者 | 权威文档 / 必须补足的边界 |
| --- | --- | --- |
| Historical archive、manifest、staging | Historical → RAW/ODS 落地、DWD | field_mapping.md / warehouse.md；一个月多 CSV、批次、全量成员、校验失败和 count 对账 |
| ODS → DWD → flow/profile/OD | 落地 → Historical 清洗 → Spark 聚合 | warehouse.md；只指定一个 DWD 产出者；跨日归桶、零小时、有效记录、分区重跑 |
| GBFS metadata → canonical station mapping / DIM | GBFS → 站点维度 → 事件适配、聚合、风险、API | field_mapping.md / warehouse.md；UUID、short_name、历史 ID 的关系和无映射行为 |
| GBFS → normalized event → Kafka consumer | GBFS adapter → 风险计算及必要的持久化 | events.md；单条 payload、key、源时间、批次、重放与消费确认边界 |
| DIM/profile + current snapshot → risk → suggestions | 数仓和事件 → 风险 → 调度 | operations.md；基线版本、时钟、计算输入、风险状态、容量与剩余可搬数量 |
| 离线聚合、当前风险/建议 → MySQL | 离线导出者及业务计算 → API | warehouse.md / architecture.md；每张服务表的 writer、主键、更新方式、整批发布与失败重跑 |
| MySQL → HTTP → 地图/详情 | API → 前端 | openapi.yaml / product.md；地图、历史日期/小时、站点分析、调度；全量或截断语义明确 |
| 真实源/录制快照 → 演示 | 各模块 → 集成验收 | runbook.md；真实 Kafka/MySQL 等路径的证据与临时 file replay 的证明范围分别记录 |

前后端契约直接共用 HTTP 数据模型。仅当展示确实需要派生状态时，在产品与交互文档中说明转换；不再增加一份重复定义字段的 view-model 协议。

## 5. 开工前必须收口的问题

这些是检查现有材料后发现的缺口或冲突。本文列出需要作出的决定，并不代替团队冻结答案。

| 问题 | 当前证据与影响 | 文档中必须给出的结果 |
| --- | --- | --- |
| **站点身份映射** | GBFS 样例的 station_id 为 UUID，station_information 同时给出 short_name；历史 ID 则是另一种字符串。仅规定 STRING 无法保证关联成功 | 定义 provider ID、canonical ID、映射来源和转换位置；验证 short_name 映射；约定未匹配、冲突、历史下线站点的处理及覆盖率口径 |
| **快照时间口径** | field_mapping.md 把 snapshot_at_utc 写成采集时间，gbfs.py 和 GBFS 交接文档使用 provider last_updated；源时间、采集时间影响过期判断 | 统一源快照时间、站点上报时间、接入时间和计算时间；分别定义缺失/null 的输入约束及向内部事件的映射 |
| **历史归桶与基线** | 先前讨论有跨小时/跨日归桶、活跃日补零和 sample_days 规则，现有字段清单不足以复现计算 | 落实已讨论规则；明确月份文件范围与业务日期的区别、跨月写入/重跑、profile 统计范围与版本；ODS/DWD 和流量守恒有适用范围 |
| **风险如何分级** | ADR-0001 给出当前 fill_ratio 阈值，同时引入 projected_bikes_1h；尚无完整规则说明两者如何共同决定 risk_type | 完整判定顺序；当前风险与预测风险的表达；无基线/过期/负库存/零容量/服务异常处理；预测原值与展示截断值的用途；“未来 1 小时”的时间窗 |
| **容量与调车数量** | 风险比例使用 bikes+docks，ADR-0002 调度目标使用 metadata capacity；30%/70% 恰好落在 LOW/HIGH 边界；均值可能产生小数数量 | 保留并明确不同容量字段的含义及约束；目标边界的准确命名；整数取整、余额扣减、平局排序、无可配对站点行为和数值算例 |
| **整批快照与新鲜度** | 事件是一站一条，建议却按快照整体重算；缺少整批完成、旧消息和上一批建议的读取规则 | 选定简单、可验证的批次发布方式；定义完整性判据、重复/乱序/部分失败、旧批次可用性和过期阈值；API 不能把不同批次拼成同一计算结果 |
| **MySQL 与运行进程** | 服务层规定读取薄表，但每张表如何导出/更新、风险消费者运行在哪里、谁实现这些入口尚未完整指定 | 明确离线导出（含 Sqoop 的实际职责）、在线写入、表结构/键/索引和发布方式；风险计算进程及 baseline 获取方式；各进程的运行时与维护人 |
| **HTTP 与 UI 状态** | 目前主要是 stations/flows 字段摘要，缺少完整路径、查询约束、错误和 freshness；mode 的 live/realtime 表述及库存字段名也需要统一 | 覆盖所有 P0 用例的 HTTP 规格；模式、字段映射、日期/小时、排序/结果上限、空与失败、新鲜度；回放不提供不存在的历史库存或风险 |
| **两种“回放”** | 历史 OD 回放和录制 GBFS 事件重放均被称为 replay，输入、用途和时间语义不同 | 分别定义页面历史模式和事件重放；演示采用的事件时钟/播放时钟、数据来源标识和 freshness 规则；不得通过改写观测时间伪装新数据 |
| **人员与排期** | #30 的分配覆盖若干适配任务，但地图页面、前端整体工程、完整 API 等主责不完整；正文又把 API/UI 启动写到 Day 6 | 给 API 和前端各落实一名主负责人，确认四位开发者兼任工作量；Day 3 即用样例开发、贯通页面；修正“进入 Day 3 还剩 6 天”为 5 天 |

HTTP 用例覆盖至少包括：可用历史日期/小时、实时地图、选定日期/小时的历史地图、站点历史 profile 与实际小时流量、当前调度建议。风险可以随站点响应提供；列表已含详情时可复用数据，不为每个 UI 操作增设接口。运营总览只按 P1 规划。

## 6. 共享样例是并行开发的实际起点

各模块使用同一组站点、日期、快照和契约版本，形成可从输入追到输出的小数据链：

历史 CSV + GBFS metadata/快照 → DWD/DIM → flow/profile/OD → risk/suggestions → MySQL 样例 → HTTP 响应。

每个箭头同时提供输入和预期输出。现有 fixtures/contracts/、fixtures/gbfs/ 和 fixtures/citibike/ 先复用，再补缺失的下游场景。标准样例中应同时出现 provider ID 与可核对的 canonical ID，避免用“所有层恰好是同一种 ID”的假数据掩盖真实问题。

| 样例组 | 必须能验收的行为 |
| --- | --- |
| 最小正常链路 | 含短缺、富余、健康站点；可手算流量、基线、风险、调车及最终响应；具体数值随规则一起冻结 |
| 历史质量与时间 | 多 CSV、重复记录、空站点、非正时长、非法时间；跨小时/跨日/跨月；活跃日内零小时与缺少该日期数据 |
| 映射与元数据 | 已映射、未映射、映射冲突、历史站点已下线、坐标或 capacity 缺失 |
| 风险与调度边界 | 15%/30%/70%/85% 边界；无基线、零容量、负数/缺失库存、服务异常；小数目标、一次来源多次匹配和无可匹配站点 |
| 事件与发布 | 完整快照、重复、乱序、部分失败、最后成功批次、过期数据、同结构重放 |
| API 与页面 | live、历史回放、空日期/小时、无基线、过期、参数非法、服务失败；查询上限/截断；切换模式时旧响应不覆盖当前选择 |

复用现有 Source/Event 校验器；表使用 DDL 和有预期结果的查询；HTTP 使用 OpenAPI 和响应样例。新增检查以能发现契约错误的最小入口为准，不另造校验平台。

Day 2 必须交付可读取、可校验的样例与预期结果。完整采集、算法、服务和 UI 的业务测试由各实现切片补上；门禁不能要求尚未实现的产品已经全链路运行。

| 1. 范围与页面 | product.md 的五条 P0 使用路径、状态及线框 | 各负责人盘点已有交付和字段缺口 | 每条页面路径的数据需求明确，P1 与 P0 分开 |
| 2. 模块与交接 | architecture.md 和契约索引；人员/目录草案 | source、数仓、事件、规则、API 分别提交本域所需输入输出 | 每个输出有生产者、消费者；API 和前端主责明确 |
| 3. 数据与规则收口 | ID、时间、表、事件、风险/调度的一致定义 | 各维护人补本域文档，生产者与消费者成对评审 | 第 5 节相关分歧都有明确决定和算例 |
| 4. HTTP、样例与运行路径 | OpenAPI、同源 fixtures、运行/验收场景 | 前端按数据样例核对页面状态；后端核对每个查询的表来源 | 所有 P0 有接口与样例，开发替身可用，检查命令可复现 |
| 5. 开工基线 | delivery.md、可执行 Issue、冻结提交与评审记录 | 全员最后核对自己的交接和工作量 | 第 9 节开工标准通过，再由组长确认 #31 |

文档可以同时起草；有依赖的定义先确定，再让下游签收。Day 2 冻结跨模块可观察行为，不提前规定所有类、内部函数、组件树或装饰细节。

### 后续七天计划的编排要求

| 项目日 | 各组共同形成的增量 |
| --- | --- |
| Day 1 | 已有真实数据和基础链路 PoC，复用验收记录 |
| Day 2 | 完成约定、样例、分工与契约评审，建立统一开工基线 |
| Day 3 | 数据、事件、规则、API、前端同时推进各自切片；用共享样例形成首个可演示的页面—API 薄链路 |
| Day 4 | 真实历史聚合、站点映射和事件输入逐步替换样例；前后端继续并行，尽早核对结果 |
| Day 5 | 贯通 Kafka、风险/调度、MySQL、API 和页面，核验批次与实际基础设施 |
| Day 6 | 集成回归，处理过期、失败、无基线和数据量等问题，决定 P1 是否交付 |
| Day 7 | 最终对账、演示、运行手册与验收证据，完成缺陷收敛和交付 |

这张表定义每日集成目标。具体工作量和人员由 delivery.md/Issues 落实，不能把表中五种开发职责误当成五位额外开发者，也不能把 Day 6 当作前后端的起始日。

## 9. 允许并行开发的完成标准

- [ ] 五条 P0 用户路径都能追溯到 API、服务表、生产者和数据来源。
- [ ] 所有跨模块接口有确定版本、字段/行为、维护人、生产者和消费者；第 5 节阻断问题已解决。
- [ ] 共享小样例覆盖正常路径和相关边界，包含明确的预期输出，检查入口可复现。
- [ ] 各负责人能说明真实上游未完成时使用哪个输入、输出给谁、如何独立验证。
- [ ] API、前端、数据导出、事件消费、共享目录/文件的主责齐全，四位组员的实际兼任安排已确认。
- [ ] 真实集成路径和证据要求已定义；fixture/file replay 的通过不能替代尚未完成的 Kafka、HDFS/Hive 或 MySQL 实测。
- [ ] 文档、Issue、ADR 后继关系和样例引用同一版基线；任务开工与最终产品验收的标准分别记录。
- [ ] 组长根据上述证据确认 #31，随后各实现任务使用同一基线并行开始。

当前仓库 CI 主要覆盖 Python 质量检查和已有契约/单元测试，部分 Spark 测试依赖本地运行环境。CI 全绿不能单独证明新文档中的所有字段已定义、API/前端已实现或真实链路已验收。
